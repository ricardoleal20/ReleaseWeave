# First ReleaseWeave release: v0.2.0

The historical ChangeForge v0.1.4/v0.1.5 releases remain unchanged. v0.2.0 is the first release under the ReleaseWeave name, retaining the documented independent-package PoC contract.

## Deliverables

- Native archives for Linux x64/ARM64 (Ubuntu 22.04 baseline), macOS Intel/Apple Silicon, and Windows x64.
- Checksummed archives containing the CLI, MIT license, quickstart and real single-repository/monorepo examples.
- POSIX and PowerShell installers with platform detection, checksum verification and user-local destinations.
- A reusable/manual native-distribution workflow: builds and smoke-tests all five targets, gathers artifacts, prepares a draft, attaches assets, verifies their presence, then publishes.
- The repository's release-on-merge workflow prepares a draft and calls native distribution directly, so publishing does not depend on another event being triggered by GITHUB_TOKEN. Consumer workflow templates keep their existing package-release behavior.
- Versioned GitHub Action usage, source installation pinned to v0.2.0, English and Spanish installation/quickstart documentation, and release notes describing supported behavior and limitations.
- New interlaced release-strand icon and banner in README, documentation and favicon references. Keep prior artwork in history; use distinctly named current assets.

## Validation and publication sequence

1. Regression tests for distribution archives/checksums, installer failures and draft publishing; observe failures before implementing.
2. Build/test/package locally and exercise an installer against locally served assets with a temporary destination.
3. Generate and inspect both new artwork assets, save them in docs/img/, and update references.
4. Use ReleaseWeave's own minor changeset/bump flow to produce v0.2.0, Cargo.lock, CHANGELOG and .releaseweave/release.json.
5. Independent review, required Linux/macOS/Windows PR CI, and a five-target distribution preflight on the release branch.
6. Merge the release PR. The existing release workflow creates the tag at the merge commit, prepares a draft, then invokes native builds and publication after all targets succeed.
7. Verify the public release, checksums, all five assets, current-host installation from GitHub, both installed-CLI examples and clean synchronized main.

No registry credentials are required: installation uses native GitHub Release assets or cargo install --git with the exact tag. The release remains pre-1.0 and documents unsupported inherited package versions, automatic dependency propagation and registry publishing.
